# Contributing to Pyrception

Thank you for taking the time to contribute!

All types of contributions are encouraged and valued. See the [Table of Contents](#table-of-contents) for different ways to help and details about how this project handles them. Please make sure to read the relevant section before making your contribution. It would make it a lot easier for maintainers, and would smooth out the experience for everyone involved.

If you like the project but just don't have time, energy or knowledge to contribute, that's perfectly fine. There are other easy ways to support the project and show your appreciation, which we would also be very happy about:

- Star the project
- Make a post about it on social media
- Refer this project in your project's README
- Mention the project at local meetups and tell your friends/colleagues

## Code of Conduct

This project and everyone participating in it is governed by the [Pyrception Code of Conduct](https://github.com/cantordust/pyrception/blob/dev/docs/code_of_conduct.md).
By participating, you are expected to uphold this code. Please report unacceptable behaviour to the maintainers.

## I have a question

If you would like to ask a question, we assume that you have read the available [Documentation](https://pyrception.readthedocs.io/en/latest/).

Before you ask a question, it is best to search for existing [Issues](https://github.com/cantordust/pyrception/issues) that might help you. In case you have found a suitable issue and still need clarification, you can write your question in this issue. It is also advisable to search the internet for answers first.

If at that point your question remains unanswered and you still need clarification, we recommend that you [open an issue](https://github.com/cantordust/pyrception/issues/new). Please provide as much context as you can about what you're running into, such as platform (e.g., Linux), language version (e.g., Python 3.12), library versions (e.g., NumPy 2.0), depending on what seems relevant. We will then take care of the issue as soon as possible.

## I would like to contribute

<!-- omit in toc -->
> ### Legal Notice
> When contributing to this project, you must agree that you have authored 100% of the content, that you have the necessary rights to the content and that the content you contribute may be provided under the project licence.

### Human vs. AI content

We have a strong preference for contributions written 100% by a human. That said, we acknowledge that a lot of code is now generated by AI, and that it can be a useful tool. By 'AI', we refer to popular usage of the term 'artificial intelligence', which includes LLM-based assistants and agents (it does not amount to a recognition of any _actual_ intelligence in said assistants and agents).

Disclosure and human review conditions apply to AI-generated content. Whether human or AI-generated, we will reject contributions that do not meet basic quality criteria.

#### Limits on AI content

If you really cannot contribute without the help of AI, it is your responsibility to ensure that any AI-generated portions, especially code, have been thoroughly reviewed, debugged and fact-checked by a human who understands what the code does.

Some examples of *unacceptable* content generated with AI assistance include:

- Auto-generated summaries and documentation (such as by feeding the codebase to AI)
- Code and documentation that is overly wordy or over-engineered (resulting in quantity but not quality)
- Contrived or meaningless tests (tests must be reviewed and address codebase functionality)
- Output that significantly diverges from the existing project architecture, style or organisation.

Some examples of *acceptable* use of AI assistance include:

- Refactoring existing code to improve speed (if needed)
- Adding concise and informative docstrings
- Testing specific functionality of the codebase (if not otherwise covered)
- Improving language or translation.

All content must be subject to thorough human review. If you cannot explain or defend your code or documentation, this will be a red flag to indicate insufficiently reviewed AI-generated content.

#### Disclosure condition

You are expected to clearly disclose any use of AI in your contribution. Issue templates may be used to make it easier for users to disclose AI assistance.

At a minimum, this must describe:

- Which parts of the code or documentation were AI-assisted and
- How AI was used (for example, ideation, drafting code, documentation or tests, spelling/grammar improvements, refactoring, bug discovery & security checks).

#### Contribution guidelines still apply

In all cases, you remain responsible for your contributions. Only submit work that meets quality standards.

### Reporting bugs

<!-- omit in toc -->
#### Before submitting a bug report

A good bug report shouldn't leave others needing to chase you up for more information. Therefore, we ask you to investigate carefully, collect information and describe the issue in detail in your report. Please complete the following steps in advance to help us fix any potential bug as fast as possible.

- Make sure that you are using the latest version.
- Determine if your bug is really a bug and not an error on your side e.g. using incompatible environment components/versions (Make sure that you have read the [documentation](https://pyrception.readthedocs.io/en/latest/). If you are looking for support, you might want to check [this section](#i-have-a-question)).
- To see if other users have experienced (and potentially already solved) the same issue you are having, check if there is not already a bug report existing for your bug or error in the [bug tracker](https://github.com/cantordust/pyrception/issues?q=label%3Abug).
- Also make sure to search the internet (including Stack Overflow) to see if users outside of the GitHub community have discussed the issue.
- Collect information about the bug:
  - Stack trace (Traceback)
  - OS, Platform and Version (Windows, Linux, macOS, x86, ARM)
  - Version of the interpreter, compiler, SDK, runtime environment, package manager, depending on what seems relevant.
  - Possibly your input and the output
  - Can you reliably reproduce the issue? And can you also reproduce it with older versions?

<!-- omit in toc -->
#### How do I submit a good bug report?

> You must never report security related issues, vulnerabilities or bugs including sensitive information to the issue tracker, or elsewhere in public. Instead sensitive bugs must be sent by email to <>.
<!-- You may add a PGP key to allow the messages to be sent encrypted as well. -->

We use GitHub issues to track bugs and errors. If you run into an issue with the project:

- Open an [Issue](https://github.com/cantordust/pyrception/issues/new). (Since we can't be sure at this point whether it is a bug or not, we ask you not to talk about a bug yet and not to label the issue.)
- Explain the behaviour you would expect and the actual behaviour.
- Please provide as much context as possible and describe the *reproduction steps* that someone else can follow to recreate the issue on their own. This usually includes your code. For good bug reports you should isolate the problem and create a reduced test case.
- Provide the information you collected in the previous section.

Once it's filed:

- The project team will label the issue accordingly.
- A team member will try to reproduce the issue with your provided steps. If there are no reproduction steps or no obvious way to reproduce the issue, the team will ask you for those steps and mark the issue as `needs-repro`. Bugs with the `needs-repro` tag will not be addressed until they are reproduced.
- If the team is able to reproduce the issue, it will be marked `needs-fix`, as well as possibly other tags (such as `critical`), and the issue will be left to be [implemented by someone](#your-first-code-contribution).

### Suggesting enhancements

This section guides you through submitting an enhancement suggestion for Pyrception, **including completely new features and minor improvements to existing functionality**. Following these guidelines will help maintainers and the community to understand your suggestion and find related suggestions.

<!-- omit in toc -->
#### Before submitting an enhancement

- Make sure that you are using the latest version.
- Read the [documentation](https://pyrception.readthedocs.io/en/latest/) carefully and find out if the functionality is already covered, maybe by an individual configuration.
- Perform a [search](https://github.com/cantordust/pyrception/issues) to see if the enhancement has already been suggested. If it has, add a comment to the existing issue instead of opening a new one.
- Find out whether your idea fits with the scope and aims of the project. It's up to you to make a strong case to convince the project's developers of the merits of this feature. Keep in mind that we want features that will be useful to the majority of our users and not just a small subset. If you're just targeting a minority of users, consider writing an add-on/plugin library.

<!-- omit in toc -->
#### How do I submit a good enhancement suggestion?

Enhancement suggestions are tracked as [GitHub issues](https://github.com/cantordust/pyrception/issues).

- Use a **clear and descriptive title** for the issue to identify the suggestion.
- Provide a **step-by-step description of the suggested enhancement** in as many details as possible.
- **Describe the current behaviour** and **explain which behaviour you expected to see instead** and why. At this point you can also tell which alternatives do not work for you.
- You may want to **include screenshots or screen recordings** which help you demonstrate the steps or point out the part which the suggestion is related to. You can use [LICEcap](https://www.cockos.com/licecap/) to record GIFs on macOS and Windows, and the built-in [screen recorder in GNOME](https://help.gnome.org/users/gnome-help/stable/screen-shot-record.html.en) or [SimpleScreenRecorder](https://github.com/MaartenBaert/ssr) on Linux. <!-- this should only be included if the project has a GUI -->
- **Explain why this enhancement would be useful** to most Pyrception users. You may also want to point out the other projects that solved it better and which could serve as inspiration.

## Style guide

### Commit messages

While there is no specific Please provide informative commit messages. This does not mean enumerating every tiny change (such as fixing a typo), but it should mention material changes that the commit introduces. Be concise (nobody wants to read verbose commit messages) and don't go into trivial details.

That said, if the commit message is just  or the message is altogether missing, maintainers may still ask you to elaborate on what you changed and why. Being *too* concise may also trigger questions about the content of the contribution, including the use of AI (see [AI policy](#human-vs-ai-content) above).

### Code formatting

Please follow the overall coding style of the existing codebase. We use the [Black](https://github.com/psf/black) formatting style for Python code, so please format your code with `black` before making a PR (it would minimise differences with existing code, making it faster and easier to review your contribution).

Please use the trailing comma to make lines shorter. Specifically, any function with more than one argument (including `self`) should have the trailing comma, which puts every argument on a separate line.

### Language

Please use **British English spelling**. This applies not only to comments and documentation, but also the code itself (e.g., `optimise()` rather than `optimize()` for a function name).

## Joining the project team

To join the project team as a maintainer with commit rights, you must first build a track record of accepted and merged contributions. Being active in discussions and replying to issues does not constitute sufficient grounds for becoming a maintainer.
